# TourGraph on Cloudflare: independent review

**Date:** November 1, 2026
**Branch:** `cloudflare-move` at `6c1f2ac`, plus the uncommitted files present during the review
**Reviewer role:** the breaker. I did not build this. I read the old system (backend/, nginx), the new Worker (web/src/server, web/worker.ts, web/src/lib/api.ts, config, scripts, tests) and the three design docs, then tested against both sites.

What I ran: `npx vitest run` (48 of 48 pass), `node scripts/verify.mjs` against workers.dev (35 of 35 pass), about 100 read only requests to workers.dev and tourgraph.ai, public DNS lookups, one TLS handshake with the droplet, and query plans on a scratch clone of `data/tourgraph.db` (deleted afterwards). Nothing was deployed, written or committed.

**Summary:** no blockers. Mail is safe under the current plan. One high finding: the switchover deletes the DNS records before the Worker can take them, which guarantees an outage window that is easy to avoid. Two medium findings: the droplet certificate (the rollback target) expires Nov 27 and is not renewing, and the D1 fingerprint can say "matches" when data differs. The rest are low.

Severity count: blocker 0, high 1, medium 2, low 11.

## R1. The switchover deletes the A records before the custom domains exist

- **Severity:** high
- **Status:** Confirmed (plan and wrangler code read; DNS looked up)

**What is wrong.** Section 9 step 2 (`docs/cloudflare-architecture.md:116`) deletes the apex and www A records, and step 3 (`:117`) attaches the custom domains afterwards. Nothing answers for tourgraph.ai in between. The reason given ("a non interactive deploy would otherwise overwrite them without asking") is the behavior we want: wrangler 4.156.0 sets `override_existing_dns_record = true` when it has no terminal (`web/node_modules/wrangler/wrangler-dist/cli.js:165533-165536`) and, with a terminal, asks "Update them to point to this script instead?" (`:165555-165563`). Either way Cloudflare replaces the record in the same API call.

The zone's SOA is `tourgraph.ai. 1800 IN SOA ... 1800`, so resolvers cache a negative answer for 30 minutes. `www` has no other records, so it becomes NXDOMAIN. The apex keeps its MX and TXT, so it gets "no A record".

**Failure scenario.** Step 3 as written is a deploy. `deploy.mjs` runs 48 tests and a full OpenNext build before wrangler touches domains, so the gap is several minutes. Any resolver that asks in that window keeps the negative answer for up to 30 more minutes. If the attach fails (token scope, a typo in the routes block, a wrangler error), the site stays down until someone recreates the records by hand, and the plan has no step for that.

**Recommended fix.**
1. Export the zone first (DNS page, Export) so any record can be restored exactly.
2. Drop step 2. Add both custom domains to `wrangler.jsonc` and attach them in one call. `npx wrangler triggers deploy` applies only routes and domains, with no rebuild. Run it without a terminal, or answer yes to the prompt.
3. Add a "failed attach" branch: recreate the two A records at 143.244.186.165 immediately. Keep the two record payloads ready to paste.
4. For rollback, do the same: have the A records ready, detach, create them at once.

Response (builder, Nov 1): Taken. Step 2 is gone. Wrangler 4.156 run without a terminal sets `override_existing_dns_record` (confirmed at `cli.js:165533-165536`), so the custom domains replace the two A records in the same call. The zone is saved as JSON and as a BIND export before the change, the two A record payloads are kept ready, and section 9 now has a failed-attach branch and a rollback that recreates them at once. The attach uses `wrangler triggers deploy` (no rebuild).

Outcome at the switchover: Cloudflare refused the replace (code 100117, "externally managed DNS records... Delete them first"), so the override does not apply to DNS-only records made outside Workers. Each hostname was then switched by a script that deletes the A record and attaches the domain immediately, with the A record recreated on failure. The gap was 484 ms for www and 451 ms for the apex, not the minutes the original plan would have taken.

## R2. The droplet certificate expires Nov 27 and is not renewing; after the switchover it cannot

- **Severity:** medium
- **Status:** Confirmed (dates); Plausible (that renewal is broken rather than late)

**What is wrong.** The droplet serves a Let's Encrypt certificate valid from Aug 29, 2026 to **Nov 27, 2026 08:23 GMT** (openssl against 143.244.186.165). Certbot renews from 30 days before expiry, so a new certificate was due from about Oct 28 and has not appeared. Renewal uses HTTP-01 on `/.well-known/acme-challenge/` (`deployment/nginx/tourgraph.conf:18-20`, `:118-121`). After the switchover that path is served by the Worker, so renewal cannot succeed.

**Failure scenario.** The rollback in section 9 points DNS back at the droplet. After Nov 27 that droplet presents an expired certificate, and browsers that have seen the HSTS header refuse with no way to click through. So the rollback quietly stops working on Nov 27. Separately, if the switchover slips past Nov 27, the live site breaks.

**Recommended fix.** Before switching, run a certbot dry run and a renewal on the droplet and find out why the timer has not renewed. Write the resulting expiry into section 9 as the end of the rollback window ("rollback to the droplet works until ...").

Response: Accepted as a dated limit, not fixed. The droplet is being retired, and fixing certbot would mean logging into it for a server that is about to go. Section 9 now says rollback to the droplet works until Nov 27, 2026 08:23 GMT or until the droplet is deleted, whichever comes first. After that, rollback is `wrangler rollback` and D1 Time Travel.

## R3. The D1 fingerprint can report a match while the data differs

- **Severity:** medium
- **Status:** Confirmed (code read; tolerance sizes measured on `data/tourgraph.db`)

**What is wrong.** `web/scripts/d1-load.mjs:134-141` applies a relative tolerance of 1e-6 to every fingerprint value, not only to sums of REAL columns. Counts, text counts, total lengths and code point sums are integers and could be compared exactly. On the real `tours` table the tolerance hides:

| Fingerprint value | Real total | Allowed difference |
|:-|:-|:-|
| total length of `description` | 83,675,884 | 83 characters |
| total length of `image_urls_json` | 148,690,311 | 148 characters |
| sum of `review_count` | 10,444,061 | 10 |
| sum of `from_price` | 66,838,371 | $66 |
| sum of `id` | 9,809,459,850 | 9,809 |

Two more blind spots, independent of the tolerance:
- The fingerprint is per column (`:104-123`). Values moved between rows (two tours' titles swapped, a one liner attached to the wrong id) give identical sums at any tolerance.
- Only the first, middle and last characters are checked. A same length change inside a string (for example a character replaced by U+FFFD) passes.

Minor: `MAX_STATEMENT` (`:32`, checked at `:161-162`) counts UTF-16 units, while D1's 100 KB limit is in bytes. A row heavy in non ASCII text could exceed it. That fails loudly, so it is low risk.

**Failure scenario.** A load bug that truncates a few descriptions, or shifts one column by a row, prints "D1 matches data/tourgraph.db for every table." The architecture doc (section 4) cites that line as the proof of the copy.

**Recommended fix.** Compare `n`, `c`, `t`, `l`, `f`, `e`, `m` exactly. Keep a tolerance only for `s` on REAL columns, and make it absolute and tiny, or sum `round(x * 100)` instead. Add terms that tie values to rows, such as `total(id * length(col))` and `total(id * unicode(substr(col, k, 1)))` for a few positions k. Then re-run the verify mode against the current D1.

Response: Fixed. Every fingerprint value is now an exact integer and compared exactly: counts, text counts and lengths, numbers as `round(x * 1000)`, and code points at positions 1, 7, 29, 101, the middle and the end. Terms weighted by `rowid % 997` tie values to rows. Statement size is counted in bytes. Checked that it fails: a pure swap of two titles (equal total length) and a one character trim both fail it. Production D1 re-verified: 505 fingerprint values across the five tables, all equal.

## R4. Next.js static files lost their year long immutable caching

- **Severity:** low
- **Status:** Confirmed (live)

**What is wrong.** On the droplet, `/_next/static/chunks/7971151b507ac939.js` is sent with `Cache-Control: public, max-age=31536000, immutable`. On the Worker, `/_next/static/chunks/1kexj4s7oxhs2.js` gets Cloudflare's asset default, `public, max-age=0, must-revalidate`. `web/public/_headers:4-10` adds only security headers. Inventory X6 listed this behavior.

**Failure scenario.** Every page view revalidates every JS and CSS chunk. Repeat visits on phones get slower. Nothing breaks.

**Recommended fix.** Add to `web/public/_headers`:

```
/_next/static/*
  Cache-Control: public, max-age=31536000, immutable
```

Add a check for it to `verify.mjs`.

Response: Fixed. `public/_headers` sets `public, max-age=31536000, immutable` on `/_next/static/*`; `verify.mjs` checks it (passes on workers.dev).

## R5. Static files skip the www and http redirects

- **Severity:** low
- **Status:** Confirmed (config and Cloudflare docs; behavior seen on workers.dev); Plausible on the custom domains until they exist

**What is wrong.** `web/wrangler.jsonc:13-16` does not set `run_worker_first`. Cloudflare serves a request that matches an asset without running the Worker ("Routing behavior" in the Workers static assets docs). The redirects live in the Worker (`web/src/server/route.ts:31-37`). On workers.dev today, `http://tourgraph.nikhil-58a.workers.dev/logo-white.png` returns 200 over plain http, which shows the asset path never reaches `route.ts`.

**Failure scenario.** After the switchover, `https://www.tourgraph.ai/social-card.png`, `/logo-white.png`, `/social-card.html`, `/BUILD_ID` and every `/_next/static/...` file answer 200 on www, and the same files are served over plain http on both names. nginx redirected every path. The result is duplicate URLs, not a security hole: pages still redirect, and HSTS covers browsers that have visited.

**Recommended fix.** Either note it as a deliberate difference, or turn on the zone's Always Use HTTPS and add one Redirect Rule from www to the apex (both run before the Worker). Setting `run_worker_first: true` also works but costs a Worker invocation per file. Add one asset path to the redirect checks in `verify.mjs`.

Response: Partly fixed, rest documented. Always Use HTTPS is now on for the zone (it acts before the Worker, so plain http redirects for every path, static files included; `verify.mjs` checks one static file on tourgraph.ai). Static files on www answering 200 is a deliberate difference (section 3): no page content, and making the Worker run first for every file would cost an invocation per file.

## R6. `/health` reports Unix time as uptime and keeps saying "ok" without D1

- **Severity:** low
- **Status:** Confirmed (live)

**What is wrong.** `web/src/server/api/env.ts:14` sets `STARTED_AT = Date.now()` at module scope. Workers return 0 from the clock outside a request, so live `/health` answers `{"status":"ok","tours":136256,"uptime":1793516866.029}`: 56 years. `health.ts:8-13` also memoizes the tour count for an hour, so after the first call `/health` never touches D1. The doc's deliberate difference ("seconds since this isolate started") is not what ships.

**Failure scenario.** Anything that uses `/health` as a liveness probe misses a D1 outage for up to an hour in a warm isolate. The uptime number is meaningless. The unit test (`web/test/api.test.ts:16`) only checks that uptime is a number.

**Recommended fix.** Set the start time on the first request instead of at import. Run a cheap `SELECT 1` on every `/health` call and keep the memo only for the count.

Response: Fixed. Uptime counts from the isolate's first request, and `/health` runs `SELECT 1` on every call (the tour count stays memoized: the data is frozen). Unit test and `verify.mjs` check the range.

## R7. "World's Most: Longest" now draws from a different set of ten tours

- **Severity:** low
- **Status:** Confirmed (live samples and local query)

**What is wrong.** 216 active tours tie at the 20,160 minute cap. The query orders only by `duration_minutes DESC` (`web/src/server/api/routes/superlatives.ts:26-30`), so which ten are kept depends on scan order. On D1 the new `idx_tours_duration` (`web/migrations/0001_schema.sql:41`) is read backwards, which returns the highest ids. The droplet answered id 5502, inside its set (947 to 5502, the same set the local file gives). The Worker answered 137782, 135371 and 137782, outside it. `shortest` (2,524 ties) and `hidden-gem` (921 ties) matched in my samples.

**Failure scenario.** Nothing breaks, but the page shows different tours than before, which the doc does not list. `contract-diff.mjs` compares superlatives by shape only (`:131-134`), so it cannot see this.

**Recommended fix.** Either add it to the deliberate differences table, or make the tie order explicit: `ORDER BY duration_minutes DESC, id` with an index on `(duration_minutes DESC, id)` so the plan stays cheap.

Response: Fixed rather than documented. All six superlative queries now end with `, id`, which reproduces the droplet's tie order: on the source file each query's top ten is identical with and without `, id`, and on D1 all six now return exactly the droplet's ten. Migration 0002 makes the duration and review count indexes descending so `longest` and `most reviewed` stay index walks (10 rows read on D1). Unit test added.

## R8. `/right-now/tours` runs one D1 statement per supplied time zone, with no cap

- **Severity:** low
- **Status:** Confirmed (live)

**What is wrong.** `web/src/server/api/routes/right-now.ts:28` drops duplicates but accepts any names, and `:47-54` keeps batching 25 at a time until `count` tours are found. One request with 600 made up zones returned `{"tours":[]}` after 2.8 s, after running 600 statements. The URL limit allows roughly 1,500 names. Batches count as one query each toward the per invocation limit, so this does not fail; it just costs.

**Failure scenario.** A small request turns into hundreds of D1 queries and seconds of Worker time. Repeated, it burns D1 reads for nothing. The droplet had the same loop, on local SQLite.

**Recommended fix.** Keep only names in the remembered time zone list (one filter, which also drops junk), and cap the list at 300. There are 289 real zones.

Response: Fixed. Only names in the remembered time zone list are queried, at most 300. 600 made-up zones now answer in 0.3 s. Unit test added.

## R9. API paths became case sensitive, and JSON lost its charset

- **Severity:** low

## R11. Trivia: the date check is narrower than recommended, and assembly is not atomic

- **Severity:** low
- **Status:** Confirmed (code); Plausible (the impossible date path, not run because it could write)

**What is wrong.**
- `web/src/server/api/routes/trivia.ts:38`, `:209` accept any string shaped like a date. Inventory O6 recommended "an existing assembled day or today". `/trivia/results?date=2027-01-01` still assembles a future day, marks five questions used, and returns the answers that day will use. About 250 such calls use up the unused pool.
- An impossible date such as `2026-13-45` passes the pattern. `formatSlots` (`:46-56`) then computes NaN, the wildcard format becomes `undefined`, and binding it should throw: a 500, with nothing written, since the INSERT comes later.
- `:102-112`: the INSERT into `trivia_daily` and the UPDATE batch on `trivia_pool` are separate calls. If the UPDATE fails, the day is saved but its questions stay unused and can be picked again.

**Failure scenario.** Low, since nobody uses trivia: questions can be burned or revealed ahead of time, and a failed write leaves the pool inconsistent.

**Recommended fix.** Assemble only for today; for other dates return what `trivia_daily` already holds, or 404. Put the INSERT OR IGNORE and the UPDATE in one `db.batch` (a transaction), with the UPDATE reading its ids from `trivia_daily` for that date, so it is atomic and safe to repeat.

Response: Fixed. `/trivia/results` assembles only today; another date returns its saved set or 404 `{"error": "No trivia for this date"}`, and impossible dates such as `2026-13-45` get 400. Saving the day and marking its questions used run in one `db.batch` (a transaction), and the UPDATE reads the ids back from `trivia_daily`, so it is atomic and safe to repeat. Unit tests added for each case.

## What I checked and found fine

- **Mail.** The plan touches only the apex and www A records. MX, SPF, autodiscover, the two enrollment CNAMEs and the Google verification TXT are other names or other types. SPF has no `a` mechanism, so proxying the apex does not change mail. No AAAA records exist to leave behind, and no CAA records exist to block Cloudflare's certificates.
- **Certificates and token.** The zone is active on Cloudflare nameservers, so Universal SSL covers the apex and www once proxied (confirm it shows Active before switching). The token's zone level Workers Routes edit is what custom domains need, per Cloudflare's Workers authorization docs.
- **Later deploys.** Wrangler only publishes custom domains when the config lists some, so a deploy without routes would not detach them. Adding them to `wrangler.jsonc` as planned is still right.
- **HSTS and preload.** The header is unchanged and present on pages, OG images, the sitemap, the 404 page, API responses and static files. Redirects carry none, as with nginx. The move does not change what includeSubDomains or preload commit to.
- **Secrets.** `web/.env` and `web/.env.local` are ignored by the root `.gitignore`, so `git ls-files` leaves them out of the staging copy. The staged build contains no key names (see R10 for the gaps).
- **API contract.** Every Hono route was compared line by line with its Express route. Status codes, error strings, JSON shapes, Cache-Control and CORS match, apart from R9 and the documented differences. CORS preflights match the droplet. Huge ids give 404 on both. Trailing slashes work on both.
- **Roulette.** The subquery returns exactly the quota and picks uniformly (20,000 trials on a small table). On a scratch clone of the real file with D1's indexes and ANALYZE, the pick uses the covering index plus rowid lookups. The seven category queries are disjoint, so the batch cannot pick a tour twice. Passing the exclude list as JSON keeps bound parameters under 100.
- **D1 limits.** A batch counts as one query toward the 1,000 per invocation. No statement is near 100 KB and no result is near the 50 MB cap that starts Nov 4.
- **Concurrency.** The per isolate memo only caches values from frozen data; concurrent misses just load twice. Transform functions do not mutate memoized rows. The trivia assembly and score races are handled.
- **In-process API.** `connection()` keeps data pages dynamic. The prerender manifest lists only `/privacy`, `/story`, `/support`, `/robots.txt`, the icons and the error pages.
- **Rate limiter.** Namespace 3001 does not collide with Recurate's 2001 and 2002. Pages never call `/roulette/hand` in-process, so the "unknown" IP fallback is unused.
- **Data load target.** `d1-load.mjs` reaches the database named in `wrangler.jsonc` using the OmSpark token from the secrets file, and refuses to load into tables that are not empty.
- **Superlatives other than longest, OG images, sitemap count, security headers and the not-found page** all match the droplet on workers.dev.
- **Outside this move:** tourgraph.ai has no DKIM or DMARC records. Not caused by the move; noted for the mail owner.
